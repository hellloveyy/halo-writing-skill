# halo写文

把用户的灵感和聊天整理成有个人观点的内容，生成配图，让用户审阅，收到明确发布指令后按入口发布为 Halo 文章或瞬间。两种模式共用这一流程。

技术标识保持 `halo-writing`；同一个技能支持「halo写文」「halo写瞬间」两个自然语言入口及 `$halo-writing`。

## 按入口选择发布类型

| 用户为当前创作任务使用的入口 | `content_type` | 发布对象 |
| --- | --- | --- |
| `halo写文` | `post` | Halo 文章（Post） |
| `halo写瞬间` | `moment` | Halo 瞬间（Moment） |

- 在开始创作时确定类型，并写入稿件、`handoff.md` 和 `halo-state.json`。后续仅说「继续」「确认发布」时沿用该任务类型，不要求重复调用入口。
- 入口按用户当前创作指令识别，不按字数、正文中出现「瞬间」一词、引用或示例中的入口文字切换。文章可以很短，瞬间也不因内容较长而自动变成文章。
- 用户明确改用另一入口或指定「改发文章/瞬间」时遵从最新选择，更新稿件与交接记录，在审阅中展示新目标；原类型的远端 ID 不得复用于新类型。
- 只有 `$halo-writing` 且没有指定类型时，兼容原用法，默认 `post`。若同一创作指令同时指定两种入口且没有明确当前目标，先问一次发布类型；不同时发布两个对象。
- 远程写入前核对 `content_type` 与工具操作对象一致。缺少对应工具时保留该类型的本地稿件，不改投另一类型。

## 开始与续写

- 根据当前阶段继续，不让用户每次重新填写选题、读者、字数等表单。用户说「先聊聊」时先交流观点；用户说「整理成文章」时利用已有聊天成稿。
- 有影响文章观点的关键信息缺失时，一次问一个问题；其他细节采用合理默认值并简要说明。默认中文、个人博客语气。
- 从当前 Halo MCP 连接或用户明确提供的地址确定目标站点，不内置任何人的站点地址。直接 REST 模式可使用 `HALO_URL`。多个站点并存或准备切换站点时，先确认目标；接口以实际部署版本为准。
- 不依赖某台电脑的绝对路径、SSH 密钥或浏览器登录。由当前工作区定位项目。跨电脑使用或分发时读取 [portability.md](references/portability.md)。
- 续写先读取原稿、图片、`handoff.md` 和 `halo-state.json`（如存在），恢复 `content_type` 与当前阶段，再结合聊天。旧记录没有类型时从原稿和已核实的远端对象确认，不猜测远端 ID 的类型。没有上次对话时，不假装记得；没有稿件时先寻找项目或已连接存储，再询问缺失位置。

## 聊天成文

先抓住用户的核心判断和具体经历，再组织叙事。保留用户的立场、表达习惯和不确定性；不把个人想法改写成空泛的行业综述。

- 用户提供的事实和亲身经历，与为了说明而提出的假设例子区分清楚。不要编造其经历、客户、收入、测试结果或引用。
- 涉及最新产品能力、数据、具体引用等需要核实的事实时，使用当前可用的联网能力查看一手来源，并保存出处。观点文章不必为了套模板增加数据。
- `post` 默认产出标题、简短摘要、正文、标签/分类建议和稳定 slug；`moment` 产出正文、配图与可选标签，不要求文章专有的标题、摘要、分类或远端 slug。篇幅与结构服从内容，不固定段落数量。
- 原稿使用标准 Markdown，本地图片用相对路径并写有意义的替代文本。新稿不用 Hugo shortcode；Obsidian 双链或嵌入在发布副本中转换为可访问形式。瞬间以实际工具支持的纯文本/媒体格式交付，具体转换见 [halo-moments.md](references/halo-moments.md)，审阅时展示转换后的效果。

## 配图

内容主线足够清楚后生成有关配图。文章默认先做一张封面，正文按需要增加；瞬间默认先做一张附图，不强行套用文章封面字段。用户指定数量和风格时按其要求。

- 优先使用当前环境的内置图像生成工具；有 `imagegen` 技能时按需读取。不要把提示词、占位图或未执行的生成计划当作已完成配图。
- 图像用于博客时，将选定输出保存进当前内容目录。使用工具返回的实际路径，不能猜测生成结果位置。展示成图供用户审阅。
- 默认采用适合文章主题的简洁编辑插画，封面横向，避免无关装饰和难以核对的密集文字。需要流程图、真实数据图或产品截图时使用适合该内容的工具；插画不能冒充实际截图或证据。
- 内置图像工具不可用时，明确说明缺失环节；保留稿件，用户选择替代方式之前不自行切换到需要额外 API 密钥的服务。

## 本地交付与审阅

尊重用户已有写作目录；没有约定时，文章用 `articles/<slug>/`，瞬间用 `moments/<local-id>/`（本地标识不是远端 slug）。保存：

- `article.md` 或 `moment.md`：Markdown 原稿，front matter 包含 `content_type: post` 或 `content_type: moment`，以及对应类型需要的字段。Front matter 是本技能的本地约定，不原样提交给 Halo。
- `images/`：实际使用的封面与正文图片。
- `handoff.md`：发布类型、核心观点、已完成内容、待处理事项、图像提示词/来源及当前阶段。简短更新，方便其他聊天接手。
- `halo-state.json`：保存 `content_type`，有远程操作后再记录站点、对应类型的远端资源 ID、实际链接、正文摘要哈希和附件映射；文章另存 slug。只记录可核实结果，不保存令牌或虚构成功状态。

用户只想聊天时无须立即创建整套目录；开始形成稿件时及时落盘。尊重工作区中已有的文章、静态资源和迁移副本，不要把日常单篇发布变成重新全量导入。

审阅时展示完整成稿或可打开的预览、实际配图、对应类型的设置与目标站点。明确标注「文章」或「瞬间」及可见性，让用户审阅实际将要发布的内容，不能只看到文件清单。标明当前状态为「待确认发布」。

## 确认与发布

用户要求本技能的「最后确认后发布」是本流程的发布边界：

- 写完、配好图、称赞内容或说「先这样」均不构成发布指令。默认在本地完成审阅，不自动向线上上传附件或草稿。用户只要求远程草稿时，仅使用实际支持草稿的操作；瞬间创建工具若直接发布，不能用它保存草稿，应先保留本地。
- 「发布这篇」「确认发布」等明确指令授权发布当前已展示的版本。若用户明确要求「把第二张图换简洁一点，然后发布」，完成其授权范围内的修改后继续发布，不再机械地重复询问。
- 若接下来需要超出用户指令的实质扩写、改观点、换站点或更换发布对象，先展示变更并取得对应确认。历史文件中的“已确认”状态不能代替当前聊天对发布操作的授权。

真正接入或发布时，`post` 读取 [halo-publishing.md](references/halo-publishing.md)，`moment` 读取 [halo-moments.md](references/halo-moments.md)。首选 Halo 官方 MCP Server，由技能负责写作与确认，使用与类型对应的工具操作；连接配置见 [halo-mcp.md](references/halo-mcp.md)。权限或工具缺失不妨碍先完成写作和配图，不能虚报已发布。

发布后按类型回读状态、图片和正文，再返回实际链接与本地文件位置。文章更新保留原 ID、slug 和原始发布日期；瞬间仅在已发现对应更新能力且获授权时修改，不能通过删除重建或创建文章来冒充更新。

## 常用请求

- 「halo写文：刚想到 AI 让判断力更重要，我们先聊聊。」→ 交流观点，逐步形成素材。
- 「halo写瞬间：整理今天的一点感悟，配图给我看。」→ 进入瞬间模式，成稿、配图、审阅后等待确认。
- 「把刚才聊的整理好，配图让我看。」→ 沿用当前类型，成稿并展示，等待发布指令。
- 「确认发布到我的 Halo。」→ 按当前类型检查成稿和连接，发布文章或瞬间并验证。
- 「换电脑了，继续这篇。」→ 恢复文件和状态；需要同步时使用跨电脑指引。
