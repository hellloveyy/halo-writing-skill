# Halo 发布与更新

只在需要接入、保存远程草稿或发布时读取。本文是操作指引，不代表当前电脑已经具备连接、凭据或发布权限。

## 连接

1. 首选 Halo 官方 MCP Server，读取 [halo-mcp.md](halo-mcp.md)，检查当前已连接服务器及实际工具目录。不要将 Codex 插件目录中的搜索结果当作 Halo 应用市场是否存在官方插件的依据。
2. 官方 MCP 使用站点 `/mcp` 端点与 `HALO_MCP_TOKEN`。先做只读请求验证地址、授权、文章/附件能力和现有文章。工具名和请求参数以实际发现的 schema 为准；不硬编码未发现的工具名。服务器未配置不等于站点不可用。
3. 没有可用 MCP 且用户选择直接 API 或该环境确需 REST 时，再使用 Halo REST API。站点由用户或 `HALO_URL` 明确指定，不默认其他人的站点；REST 个人令牌来自 `HALO_TOKEN`。MCP 专用访问密钥与 REST 个人令牌不能混用，也不能用 REST 绕过 MCP 密钥的工具授权限制。
4. REST 缺少令牌时指导用户在 Halo「个人中心 → 个人令牌」创建所需授权，通过环境变量配置。两种连接都不要索取后台密码，不让用户在聊天中粘贴密钥，不读取、打印或同步历史凭据文件。只报告可用性，不输出授权头；申请任务需要的文章与附件权限即可。

API 使用 HTTPS 与 `Authorization: Bearer <token>`。在进程内从环境读取令牌，避免把真实值写进命令参数、脚本、报告或日志。不要开启请求调试来打印 Authorization。认证信息不随重定向发往其他主机。

## REST 备用方案：接口证据与请求体

使用官方 MCP 时以工具输入/输出 schema 完成操作，不需要自行构造下面的 REST 请求体。只有采用直接 REST 方案时才使用本节。

官方入口：

- [REST API 与个人令牌](https://docs.halo.run/developer-guide/restful-api/introduction)
- [API 在线文档](https://api.halo.run/)
- [Halo 官方源码与版本](https://github.com/halo-dev/halo)

以下 Console 路由在已查阅的官方 API 文档中存在，具体请求体和当前部署版本仍须核对：

| 操作 | 方法与路径 |
| --- | --- |
| 查询文章 | `GET /apis/api.console.halo.run/v1alpha1/posts` |
| 创建草稿 | `POST /apis/api.console.halo.run/v1alpha1/posts` |
| 更新文章 | `PUT /apis/api.console.halo.run/v1alpha1/posts/{name}` |
| 读取/更新正文 | `GET` / `PUT /apis/api.console.halo.run/v1alpha1/posts/{name}/content` |
| 发布 | `PUT /apis/api.console.halo.run/v1alpha1/posts/{name}/publish` |
| 上传附件 | `POST /apis/api.console.halo.run/v1alpha1/attachments/upload` |

`{name}` 是 Halo 资源 ID，不是文章标题或 slug。不要把 Extension API 的裸 Post 对象直接当作 Console 创建草稿的请求体。查看对应版本的 OpenAPI 请求与响应定义；在线文档若高于实际版本，使用部署版本的定义或官方对应版本源码核实。不要根据表格猜测请求体。

特别确认正文更新的 Markdown 原文、内容类型与渲染内容字段，以及编辑器标记。保留真正可再次编辑的 Markdown，不能只把 Markdown 文本塞进 HTML 字段，或只更新文章元数据就声称正文已同步。需要渲染器时优先使用项目已有能力；缺少依赖时明确处理，不悄悄修改全局环境。

分类和标签须解析成 Halo 中实际的资源引用，不能把显示名称直接当作 ID。封面、摘要、评论设置、可见性和发布日期以用户意图及已有文章设置为准，不重置其他字段。

## 在授权范围内提交

1. 读取当前文章和 `halo-state.json`。有文章 ID 时先验证其站点、slug 与目标一致；没有 ID 时按准确 slug 查重，逐页查询直到能判断，不只看第一页。匹配多个对象时停止并澄清。
2. 构建发布副本，保留本地原稿。上传缺少的附件，并用服务器返回的真实永久链接替换副本里的本地图片路径与封面。复用已验证的同内容附件映射，不猜 `/upload/` 地址。
3. 按实际工具 schema 上传图片，确认存储策略及权限；直接 REST 方案按对应接口使用 multipart。远程 MCP 无法直接读取本机路径，必须通过其支持的文件内容或 URL 输入传输。所有预期图片上传成功并能读取后，再提交正文。图片失败时不发布含断图的版本；记录已完成附件，以便继续而非重复上传。
4. 新文章先创建草稿并及时记录服务器返回的 ID；已有文章更新同一资源及正文，保留版本字段与并发控制信息。提交前重新读取：若线上出现本地未知的更新，先比较差异，不能直接覆盖。
5. 仅获草稿授权时到此结束。已获发布授权时，按对应版本的发布操作发布当前正文/快照。不要假设设置一个布尔值就等于发布最新正文。
6. 回读正文、元数据和发布状态，并检查实际文章页面及图像。使用返回的 permalink，或从公开页面发现链接，不硬编码文章 URL 路由。部署异步生效时进行有限次数只读检查。
7. 成功后保存站点、ID、slug、permalink、正文摘要哈希、附件哈希和永久链接、核实时间。原始发布日期不因日常改稿重置。

读写失败时区分认证失败、权限不足、内容冲突、接口不兼容和网络错误。输出必要的状态码与经过清理的简短原因，不输出可能含凭据的完整响应或原始请求。

创建、上传或发布请求超时后，先只读检查远端结果，再判断是否重试；不能直接重复 POST 创建文章。接口仍不匹配时保留本地稿件和已知远端状态，说明具体阻碍。不要升级成 SSH 改数据库、重新全量导入或全站恢复。

## 发布边界

当前用户要求最后确认后发布，确认规则以主技能为准。工具应执行用户已授权的最终操作，不为普通的准备步骤增加多轮审批；若确实缺少凭据，只请求其在环境中配置，继续完成不依赖凭据的内容工作。
